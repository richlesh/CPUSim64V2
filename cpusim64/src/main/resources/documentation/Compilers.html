CPUSim64 Compilers

The IDE can edit, compile, run and debug programs in languages other than CPUSim64 assembly. Each language is a compiler plug-in: a folder of files that the IDE finds at start-up and lists under File → New Compiler. A plug-in contains a compiler that is itself a CPUSim64 program (assembled from .asm files), so adding a language needs no change to the IDE.

This document describes the plug-in architecture, the files a plug-in needs, and the compilers that come with CPUSim64: C11, C++14, VB.NET, MMIX and Rust.

Plug-in architecture

The compilers live in the compilers/ folder of the source tree. The installed application has a copy next to CPUSim64IDE.jar. A source checkout run from IntelliJ IDEA uses the compilers folder next to the ide folder; -Dcpusim64.compilers=DIR overrides it.

The IDE does not run the compilers from that folder. It uses only the plug-ins in the user's folder:

PlatformPlug-in folder
macOS, Linux~/.cpusim64/compilers
Windows%USERPROFILE%\.cpusim64\compilers
  • On its first run the IDE copies the built-in plug-ins there. On later runs (after an update, for example) it copies again the files that are newer in the built-in plug-ins.
  • Files in the user's copy that are newer than the built-in ones (your own changes) are kept.
  • When a plug-in is updated, its assembled compiler in obj/ is deleted so that it is rebuilt.
  • tests/, obj/ and output/ folders are not copied.
  • The built-in folder is never used or changed. If a plug-in's folder cannot be written to, the IDE builds a copy in ~/.cpusim64/cache/compilers.

Every sub-folder that contains a config.properties file is a plug-in. The folder name is the plug-in's name: it is the menu item under File → New Compiler and the title of the window.

compilers/
    C11/
        config.properties    required
        cc.asm, ...          required: the compiler's assembly sources
        system_prompt.md      optional: the AI Chat prompt for this language
        README.md                by convention: documentation for people

    C++14/ ...

Two kinds of compiler

The compiler program takes the path of a source file as its argument, writes <source>.asm next to the source, and exits with 0 on success. A plug-in does this in one of two ways.

Direct compiler
The compiler writes the CPUSim64 assembly itself. The C11 compiler is written in CPUSim64 assembly. The MMIX translator and the VB.NET compiler are written in C and compiled by the C11 compiler, then assembled like any other program.
Translator (translate_to)
The compiler writes source code in another language, <source>.gen.<ext>, and the IDE runs the plug-in named by translate_to on that file. The C++14 and Rust plug-ins translate to C and use the C11 compiler to finish the job. The translators emit #line directives, so the debugger shows the original source lines.

system_prompt.md

The AI Chat in a CPUSim64 window is told how to write CPUSim64 assembly, using the documentation in doc-index.txt. A compiler window is about another language, so the chat uses the plug-in's system_prompt.md instead. Write it as instructions to an assistant that helps a user with programs in that language. A good prompt covers:

  • what the window does (for example: translates the source to C, compiles it and runs it);
  • the program conventions: where execution starts, how arguments and input arrive, how the exit code is set, what the Options field takes;
  • the supported language and library, and what is not supported, so the assistant does not write code the compiler rejects;
  • the representation differences a user can observe (word sizes, character width, sizeof);
  • the error message format, so the assistant can interpret what is in the console.

Without this file the plug-in works, but its chat window has no language-specific instructions.

README.md

The IDE does not read README.md. By convention each plug-in has one that tells a developer how to use, build, test and extend the compiler: usage, supported and unsupported features, the file layout, and the build and test commands. Keep it in step with system_prompt.md, which carries the same facts for the AI.

What Run and Debug do

  1. The IDE saves the file and assembles the compiler into obj/ if it is missing or out of date. Errors from this step appear in the console.
  2. It runs the compiler on the Java or native simulator (as selected in Settings) with the source file path as its argument, using compiler_mem and compiler_stack. The compiler must write <source>.asm and exit with 0; its error messages (file:line: error: message) go to the console and stop the run.
  3. For a translator, the compiler writes <source>.gen.<ext> and the translate_to plug-in compiles that.
  4. The IDE assembles the result into obj/<name>.o64 and runs it with the Args from the toolbar. A source with #export or #extern is linked with the modules it includes.

The Options field of a compiler window holds extra compiler arguments: other source files of the program (relative to the source file), -lstd for the C11 compiler, and so on.

Debugging. If the generated assembly contains .source "file", line directives (the C11 compiler and the MMIX translator emit them), the debugger shows the original source file in the compiler window. The execution marker and the breakpoints use the source lines; stepping is still by CPUSim64 instruction. Without the directives the generated assembly opens in a regular window with the debugger.

Entry point. Run and Debug are enabled for a file that is a program: one that defines main_function, has the entry_label in column 1, or matches entry_pattern.

Writing a compiler of your own

  1. Create ~/.cpusim64/compilers/<name>/.
  2. Add config.properties with at least compiler_source, and the compiler's .asm files. The compiler reads the file named by its first argument (see iARGC/iARGS in the Interrupt Reference) and writes <source>.asm.
  3. Optionally add system_prompt.md and README.md.
  4. Open a new window. The plug-in is in File → New Compiler.

The easiest route is to write the compiler or translator in C, as the bundled ones are, and compile it with the C11 compiler (compilers/C11). Set translate_to: C11 to emit C and let the C11 compiler do code generation. Name your plug-in folder differently from the built-in ones; a built-in plug-in with the same name is updated by the IDE.

C11

Folder: compilers/C11   Extensions: .c, .h   Type: direct compiler, written in CPUSim64 assembly

Architecture

The C11 compiler is the foundation of the other compilers. It is written entirely in CPUSim64 assembly and is the only compiler that does not depend on another one. The grammar follows the ANTLR grammars-v4 C grammar. Its pipeline is:

source → lexer → preprocessor → parser + semantic analysis → code generation per function → .asm
FilePurpose
cc.asmMain program: options, one or several translation units.
lexer.asm, pp.asmTokens, and the token-level preprocessor.
parse_expr.asm, parse_decl.asm, parse_stmt.asmRecursive-descent parser with precedence climbing for binary operators.
sema.asm, types.asm, symtab.asmType checking and implicit conversions (applied while parsing), type objects, scoped symbol table.
ast.asmAST nodes and the --ast dumper.
codegen.asm, runtime_emit.asmStack-machine code generation, and the assembly run-time routines copied into a program on demand.
lib/The C library, written in C.
  • The compiler stops at the first error, prints file:line: error: message to standard error and deletes partial output.
  • Values are computed into r0 (integers, pointers, aggregate addresses) or f0 (double). Arguments are pushed right to left, using the same convention as the assembly #def_func, so CPUSim64 library functions can be called directly.
  • A header #include <name.h> is found in lib/, and lib/name.c is appended once to the translation unit; only the functions the program uses are compiled.
  • cc main.c util.c compiles each file to its own relocatable module for the CPUSim64 linker (external symbols exported, static ones private). -lstd links the library as shared modules instead of appending a copy to each file.
  • It emits .source directives, so the debugger shows the C lines. #line N "file" renumbers lines, which lets a translator that emits C be debugged on its own source.
  • Debugging dumps: --pp (preprocessed source), --tokens, --ast.

Language

  • Types: char, short, int, long, long long, signed/unsigned, _Bool, double, void, pointers, multi-dimensional arrays, struct, union, enum, typedef, function pointers; the qualifiers const, volatile, restrict; static, extern, inline.
  • C99: compound literals, designated initializers, // comments, mixed declarations and code, declarations in for, variadic functions, __func__.
  • C11: _Static_assert, _Thread_local (thread_local).
  • Statements and expressions: all of them, including switch, goto, all operators, casts, sizeof, brace elision, string literal concatenation.
  • Preprocessor (built in): #include, object-like and function-like #define with #, ## and __VA_ARGS__, #undef, #if, #ifdef, #ifndef, #elif, #else, #endif, defined, #error, #line. #pragma and #warning are ignored.
  • CPUSim64 extensions: the intrinsics __ldb(byte_addr) and __stb(byte_addr, v), which compile to the LDB and STB instructions.

Library

The C library is written in C (lib/) and is compiled only when used.

  • <stdio.h>: files in all modes (r w a, +, b, x), fseek/ftell, fgetpos/fsetpos, getline, tmpfile; the exact C99 printf and scanf families including snprintf and the v variants; floating-point output rounded half-to-even like glibc, and correctly rounded input.
  • <stdlib.h>: malloc family, exit, atexit, system, getenv, strto*, rand/srand, qsort, bsearch, div family.
  • <string.h>, <ctype.h>, <math.h> (C99 functions including fma, cbrt, expm1, log1p), <time.h> (time returns the real UTC wall-clock time; strftime, timespec_get), <setjmp.h>, <assert.h>, <stdarg.h>, <stddef.h>, <stdint.h>, <stdbool.h>, <limits.h>, <float.h>.
  • <threads.h>: C11 threads, mutexes, condition variables, call_once, thread-specific storage. <stdatomic.h>: atomic types and operations.
  • POSIX subset: <unistd.h> (fork, getpid, sysconf, sleep, usleep) and <sys/wait.h> (waitpid, wait).
  • <_Thread.h>: CPUSim64's own threading header: threads, fork, shared memory, atomics, spin locks, mutexes.

Left out, and differences from the standard

  • Not supported (reported as errors): float, long double, _Complex, _Atomic, _Generic, bit-fields, variable length arrays, K&R parameter lists, GNU extensions.
  • Every scalar is one 64-bit word. char, short, int and long are all 64 bits and do not wrap at their nominal widths. sizeof and malloc count words, so sizeof(char) == sizeof(int) == 1. CHAR_BIT is 64. Programs written with sizeof stay correct; programs that assume 8-bit bytes or 32-bit overflow do not.
  • char holds a Unicode codepoint, one per word. Text files are UTF-8 on disk. Binary streams read and write one byte per char, so fwrite of an int keeps only its low byte.
  • __STDC_NO_ATOMICS__ is defined because _Atomic is not supported: the atomic_* types are volatile typedefs, and x++ on an atomic_int is not atomic. Only the atomic_* functions are.
  • Streams are unbuffered; setvbuf is accepted and has no effect. There are no locales beyond "C". localtime equals gmtime (UTC only).
  • qsort is a heapsort and not stable. rand is a deterministic 64-bit LCG, not the one in glibc.
  • The simulator's floating-point compare treats NaN as equal to everything; use isnan() instead of x != x. The isnan family are functions, not macros.
  • Every mutex is recursive. waitpid reports status 0 because the simulator does not report a child's exit status.
  • _Thread_local: &x passed to another thread points to that thread's own copy; threads created before main get no copy; the copies use stack space.
  • setjmp may be used only where C allows it (the whole condition of an if, switch or loop, an expression statement, and similar).
  • As in standard C, a library function must be declared by its header; calling it without the header is an "implicit declaration" error.

C++14

Folder: compilers/C++14   Extensions: .cpp, .cc, .cxx, .hpp, .h   Type: translator to C (translate_to: C11)

Architecture

The translator cppc is written in portable C and compiled by the C11 compiler. It translates prog.cpp into prog.gen.c with #line directives that name prog.cpp, and the C11 compiler turns that into assembly, so the debugger shows the C++ lines. The hand-written parser follows the ANTLR grammars-v4 CPP14 grammar (tests/antlr_check.sh compares them).

lexer.c, pp.c, parser.c, ast.cTokens, preprocessor, parser, syntax tree.
types.c, sema.cTypes, name lookup, overload resolution, conversions.
tmpl.cTemplates: instantiation, deduction, specialization, SFINAE. Templates are checked when instantiated, not when defined.
lambda.c, constexpr.c, braced.c, exc.cLambdas, constexpr evaluation at translation time, braced initialization, exceptions and RTTI.
translate.c, gen.cLowering to C (vtables, constructors and destructors, name mangling) and C output.
lib/The C++ standard library subset, written in C++ and translated with the program.

Programs of several .cpp files list the other files in the Options field. The IDE translates each file (the others with cppc --unit), compiles the C files as modules of one program (cc main.gen.c shapes.gen.c -lstd) and links them. Functions defined in a class, inline functions, template instances and library code are compiled into every unit that uses them, with internal linkage.

Language

  • Classes: constructors and destructors, copy and move semantics, operator overloading, conversions, access control, friends, static members, nested classes, single and multiple inheritance, virtual functions, abstract classes, override/final, delegating and inheriting constructors, = default/= delete.
  • Templates: function, class, member, alias and variable templates; default arguments; non-type parameters; explicit and partial specialization; argument deduction; SFINAE (enable_if); variadic templates (sizeof..., pack expansion).
  • C++11/14: auto (also as a return type), decltype, range-for, nullptr, lambdas (captures by value and reference, init-captures, mutable, generic lambdas), rvalue references, std::move/std::forward, std::initializer_list, uniform initialization, constexpr functions, static_assert, enum class, placement new.
  • Exceptions: throw, try/catch by type, reference and ..., rethrow, unwinding with destructors (including partly built objects), std::terminate for an uncaught exception.
  • RTTI: typeid, std::type_info, dynamic_cast for pointers and references (down and cross casts), std::bad_cast.
  • C++17 additions: if constexpr, structured bindings, if/switch with an initializer, inline variables, nested namespace definitions, [[nodiscard]] and [[maybe_unused]] (accepted).

Library

  • Streams and strings: <iostream>, <iomanip>, <sstream>, <string>.
  • Containers: <vector>, <array>, <list>, <map>, <set>, <unordered_map>, <unordered_set>, <stack>, <queue>.
  • Algorithms and utilities: <algorithm>, <numeric>, <iterator>, <utility>, <functional> (std::function, function objects, std::hash), <memory> (unique_ptr, shared_ptr, weak_ptr), <type_traits>, <initializer_list>.
  • Errors and RTTI: <exception>, <stdexcept>, <new>, <typeinfo>.
  • C headers: <cstdio>, <cstdlib>, <cstring>, <cmath>, <cctype>, <climits>, <cstddef>, <cstdint>, <cassert>, <ctime>, <cfloat>, and the POSIX <unistd.h> and <sys/wait.h>.
  • Concurrency: <thread>, <mutex>, <condition_variable>, <atomic>, <chrono>, built on the C library's <threads.h>, <stdatomic.h> and <time.h>.

Left out, and differences from the standard

  • Not supported (reported as errors): virtual base classes, pointers to members, user-defined literals (so no 100ms), fold expressions, decltype(auto), function-try-blocks, bit-fields, variable length arrays.
  • Differences from g++: int, long and pointers are 64-bit words, float is a double, char holds a Unicode codepoint, sizeof counts words, and type_info::name() returns the C++ spelling of the type, not a mangled name.
  • Threads: std::thread and std::call_once take the callable and arguments by value (a reference parameter needs std::ref); member function pointers cannot be thread targets; locking a std::mutex twice in one thread does not deadlock; std::system_error is never thrown (misuse calls std::terminate); std::atomic<T> works for integers, bool and pointers only, and every memory_order is accepted and ignored. A thread must not use the address of a local of a function that may return first.
  • Missing library parts: std::future/std::async, shared_mutex, condition_variable_any, locales. The <thread.h> wrapper for CPUSim64's <_Thread.h> still works but is deprecated.

VB.NET

Folder: compilers/VBNET   Extension: .vb   Type: direct compiler, written in C

Architecture

The compiler vbc is written in the C subset that the C11 compiler accepts and is itself a CPUSim64 program (vbc.asm). It follows the Visual Basic Language Specification version 11 (dotnet/vblang) and its grammar (grammar/vb.g4), plus interpolated strings, ?., NameOf, &B literals, digit separators and multi-line strings. Run and Debug are enabled for a file with Sub Main or Function Main (entry_pattern). It needs about 4M words of memory; the plug-in gives it 16M.

src/lexer.c, parser.c, ast.cLogical lines and #If conditional compilation; recursive-descent parser following vb.g4 (checked against ANTLR with tests/antlr_check.sh).
src/types.c, sema_*.cTypes, symbols and semantic analysis. Separate files for generics (monomorphization), lambdas, delegates and anonymous types, and query expressions.
src/codegen.c, codegen_stmt.cCode generation. Only methods that can run are generated, so the library costs a program only what it uses.
rt/Run-time library in C, compiled by the C11 compiler: memory manager and garbage collector, strings, formatting, I/O, threads.
lib/.NET library written in VB: System.vb, Collections.vb, Linq.vb, Threading.vb. It is part of every program that uses it.
  • Every value is one 64-bit word. Integer, Short, Byte and the others are checked against their ranges, and arithmetic is overflow-checked. Single values are rounded to 32 bits. Char is a Unicode codepoint; String is an object of codepoints.
  • Objects have two header words (a type descriptor and the garbage collector's word). Structures are values in boxes that are copied. Virtual methods use vtables and interfaces use itables. Generics are instantiated per set of type arguments. A lambda is a method whose Me is an environment object of the captured variables.
  • Exceptions use a chain of handler records; Finally runs on every exit. Run-time errors are catchable .NET exceptions. An unhandled one prints Unhandled exception. System.OverflowException: ... and ends with exit code 1.
  • A mark-and-sweep garbage collector (precise for the heap, conservative for the stack) runs when the allocation since the last collection exceeds the live data.
  • Errors are reported as file:line: error: message, mostly with Microsoft's messages. Compilation stops at the first error.
  • Options: --define=NAME[=VALUE], --tokens, --syntax, --ast, --parse-only, --gc-stress, --rt=DIR, --lib=DIR.

Language

  • Modules, classes, structures, interfaces, enums, delegates, namespaces, Imports, Partial classes, programs of several files (the others in Options).
  • Fields, constants, methods (ByRef, Optional, ParamArray, named arguments, overloading), constructors, properties (indexed, Default, auto-implemented), events (RaiseEvent, AddHandler, Handles, WithEvents), operator and conversion operators.
  • Inheritance (Overridable, Overrides, MustOverride, MyBase), interface implementation, TypeOf, DirectCast, TryCast, CType.
  • Generic types and methods with constraints and type inference.
  • All statements except On Error/Resume: If, Select Case, loops, Exit, Continue, GoTo, Try/Catch/When/Finally, Throw, Using, With, SyncLock, ReDim, Static locals.
  • Lambdas and closures, AddressOf, extension methods, nullable values (Integer?), ?., anonymous types, object and collection initializers, local type inference, LINQ (methods and query expressions).
  • Option Strict, Explicit, Infer and Compare.

Library

  • Console, Math, Convert, String and Char methods, Parse/TryParse, Environment, GC, .NET format strings (invariant culture), and the Microsoft.VisualBasic functions (Len, Mid, InStr, Val, Format, Rnd, vbCrLf, ...).
  • System.Exception and the standard exception classes.
  • List, Dictionary, HashSet, Stack, Queue, KeyValuePair, StringBuilder, Random (the .NET generator, so seeded sequences match), Array, Tuple, Nullable.
  • Action, Func, Predicate, Comparison, EventHandler; System.Linq.Enumerable with the query operators and aggregates.
  • File, StreamReader, StreamWriter.
  • System.Threading: Thread, Interlocked, Monitor (Enter, Exit, TryEnter), SyncLock, Environment.ProcessorCount. Console output is thread-safe.
  • CPUSim64.Process.Fork(), Wait(pid) and WaitAll() (not a .NET API): processes with a copy of the memory, as the simulator's iFORK makes them.

Left out, and differences from the standard

  • Not supported (reported as errors, "... not supported yet"): Async/Await, Iterator/Yield, late binding, On Error, Decimal and Date, XML literals, reflection (GetType), My, arithmetic on nullable values, Custom events, variance, ThreadPool and Task, Monitor.Wait/Pulse.
  • New Object() and New String(c, n) are not supported. Lock an object of a class of your own; use StrDup(n, c).
  • The library is a subset of the .NET Framework and the culture is invariant; there is no .NET assembly loading, no System.IO beyond File and the stream reader and writer, and no networking, GUI or database classes.
  • While other threads run, the garbage collector waits; it runs again when they have ended.
  • The expected output of the tests was worked out from the .NET documentation, since no .NET was available to compare with.

MMIX

Folder: compilers/MMIX   Extension: .mms   Type: translator, written in C

Architecture

This plug-in runs programs written in MMIXAL, the assembly language of Donald Knuth's 64-bit MMIX computer (The Art of Computer Programming), by translating them to CPUSim64 assembly. The translator mmixc is written in portable C and compiled by the C11 compiler. Run and Debug are enabled for a file with the label Main in column 1 (entry_label).

  • src/mmixal.c is the assembler front end. It assembles exactly as Knuth's mmixal does (PREFIX, GREG, local labels, future references, the same error messages).
  • src/gen.c writes the CPUSim64 program. Each MMIX instruction becomes a short sequence labelled M_<address>, with .source directives so the debugger shows the .mms lines and takes breakpoints in them.
  • The local registers are a window of the register stack (r27 points to $0, r26 is rL); the global and special registers are arrays in the run-time library.
  • MMIX memory is a block of the CPUSim64 heap that holds the four segments; each MMIX octabyte is one 64-bit word, big-endian. An address outside the allocated segments stops the program. Indirect jumps use a jump table with one entry per tetrabyte of code.
  • rt/mmix_rt.c is the run-time library: start-up, multiplication and division, bit-matrix and saturating operations, a port of Knuth's mmix-arith for floating point (so results, rounding and flags are those of the real mmix), exceptions and trips, TRAP and SAVE/UNSAVE. rt/mmix_io.asm has the functions that need CPUSim64 instructions or interrupts.

Options: --data=N, --pool=N, --stack=N (segment sizes in bytes, suffixes K, M; defaults 1M, 512K, 512K), --rt=DIR, --dump. The program receives $0 = argc and $1 = argv, and its exit code is $255 at TRAP 0,Halt,0.

Several files. The files listed in Options are treated as if concatenated after the main file, as Knuth intended for sharing code in MMIXAL. The location counter, symbols and local labels carry over, but each file starts with PREFIX : and its own line numbers, so errors name the right file and line. A library file starts with PREFIX Name:, and the program refers to its symbols as Name:symbol.

Language

  • All user-mode instructions: integer, logic, shifts, the conditional set and zero-or-set families, branches, loads and stores of every size, CSWAP, GETA, GO.
  • The register stack: PUSHJ, PUSHGO, POP, SAVE, UNSAVE, GET/PUT with the rules for rL.
  • Every floating-point instruction with the four rounding modes, short floats, the epsilon comparisons (rE), the arithmetic flags and trips (rA, handlers at #10 to #80, TRIP to location 0, RESUME).
  • The MMIXware simulator's system calls: Halt, Fopen, Fclose, Fread, Fgets, Fgetws, Fwrite, Fputs, Fputws, Fseek, Ftell. StdIn, StdOut and StdErr are the console.

Left out, and differences from the real MMIX

  • Kernel features: virtual memory, LDVTS, interrupts, the timer and privileged special registers are not supported. They are reported at run time on standard error.
  • Also not supported: PUT rG with a different value; RESUME with an instruction to execute in rX; programs that execute data or code they stored themselves; jumps outside the text segment.
  • An illegal instruction stops the program with exit code 1 (the real mmix stops and reports it on standard output). The exit code is $255, where the real mmix returns its low 8 bits.
  • A label may be used before it is defined only where mmixal allows it. There is no linker and no include; share code by listing files in Options.
  • The tests compare with the real mmixal and mmix (tests/run_tests.sh, and the randomised tests/random_diff.sh), which must be installed to regenerate the expected files.
  • The MMIX versions of the documentation projects leave out the ones that use threads or processes.

Rust

Folder: compilers/Rust   Extension: .rs   Type: translator to C (translate_to: C11)

Architecture

The Rust plug-in follows the design of the C++14 plug-in. The translator rustc is written in portable C and compiled by the C11 compiler. It translates prog.rs into prog.gen.c with #line directives that name prog.rs; the C11 compiler does the rest, so the debugger shows the Rust lines. The translator is one translation unit (src/rustc.c includes the other files). Errors are reported as file:line: error: message. The stages are listed in plan.md.

lexer.c, parse_*.c, ast.cTokens, parser (it follows the ANTLR Rust grammars in grammar/), syntax tree.
expand.cBuilt-in macros, macro_rules! and derive.
resolve.c, collect.cModules, use, name resolution, items, impls and traits.
check.c, types.c, moves.cType inference with trait bounds, method lookup, move and mutability checks.
cg_types.c, cg_expr.cMonomorphization and C output (enums, match, closures, vtables, drops, #line).
lib/The standard library written in Rust (core.rs, collections.rs, rc.rs) and the C runtime rust_rt.c. std and alloc are aliases of the crate core.

Every scalar is one 64-bit word. u8 data in strings, arrays and Vec<u8> is packed 8 bytes per word and accessed with the LDB and STB byte instructions; &str is a (byte address, byte length) pair. Generics are monomorphized.

Language

  • Items: functions, structs (named, tuple, unit), enums with data, impl blocks, traits (default methods, associated types and constants, dyn Trait through vtables), generics by monomorphization with bounds and where clauses, modules in one file, const, static, type aliases, operator overloading, Drop.
  • Expressions: let with patterns (and let ... else), if/if let/while let, match with guards, ranges and slice patterns, labeled loop/while/for, ranges, closures (Fn, FnMut, FnOnce, boxed), references and slices, ?.
  • Derives: Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Default, Hash.
  • Macros: println!, print!, eprintln!, format!, write!, writeln!, panic!, assert!, assert_eq!, assert_ne!, vec!, matches!, dbg!, unreachable!, todo!, and your own macro_rules!. Format strings support positional, named and inline arguments, width, precision, fill, alignment, {:?}, {:#?} and the x X o b e E types.

Library

The library is Rust source in lib/, translated with the program: Option, Result, Box, String and &str, Vec, slices, iterators with the usual adapters, fmt, io (stdin, read_line, lines, Write), mem, cmp, integer, f64 and char methods, Error with Box<dyn Error>; HashMap, HashSet, BTreeMap, BTreeSet, VecDeque, BinaryHeap; Rc, Weak, Cell, RefCell, and single-threaded stand-ins for Arc and Mutex.

Checks, panics and debugging

  • The translator checks types, trait bounds, moves and mutability.
  • Panics behave like the debug build of rustc: integer overflow, division by zero, index out of bounds, unwrap/expect failures and panic! print a message to stderr and end the program with status 101 (no unwinding, no destructors).
  • rustc --tokens, --ast, --expand, --resolve and --types print the intermediate stages.
  • tests/run_tests.sh runs the lexer, parser, expansion, resolution, type and error tests and 78 programs whose output, exit status and panic message are compared with rustc 1.97.

Left out, and differences from the standard

  • Not supported: impl Trait outside argument and return position, i128/u128, async/await, procedural macros, inline unsafe assembly, std::thread.
  • f32 is not a separate type; it is an f64.
  • Borrow checking: moves and mutability are checked, but lifetimes are not, so some programs that rustc rejects will be accepted.
  • Arc and Mutex are single-threaded; env::args() gives only the program name; HashMap has no hasher parameter; Rc works only for sized types.
  • The f64 functions sin, exp, ln and similar are within a few ulp of libm, not bit for bit.
  • As in the other plug-ins, char and integer types are word-sized in the generated C, and size_of counts 8 bytes per word.

How the compilers build on each other

C11 compiler (CPUSim64 assembly)
    compiles the C source of:
        vbc   (VB.NET compiler)       → VB.NET programs
        mmixc (MMIX translator)       → MMIXAL programs
        cppc  (C++ translator)        → C, then the C11 compiler again
        rustc (Rust translator)       → C, then the C11 compiler again

Each of these compilers is built with its plug-in's build.sh, which runs the C11 compiler on the C sources and writes the compiler's .asm file. The generated .asm files are committed because the IDE assembles them. With build.sh --native the same C sources are built with the host C compiler, which is faster for development and lets the tests compare the translators' output with g++ or the real mmix.

See also the Programmer Guide for the assembly language the compilers generate, the Directive Reference for #export, #extern and the linker, and the Interrupt Reference for the system interface that the run-time libraries use.
